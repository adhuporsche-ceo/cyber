# 1. Executive Summary

NETPROBE is an automated network and website security assessment tool designed for authorized defensive security testing. It discovers exposed network services, identifies protocols and software versions, checks website security configurations, correlates detected versions with locally stored vulnerability intelligence, calculates risk, and produces security reports.

The project addresses the difficulty of manually collecting and interpreting security exposure information. Instead of reporting only that a port is open, NETPROBE attempts to explain what service is running, what product and version were detected, whether a security weakness is present, what evidence supports the result, how confident the detection is, and what remediation is recommended.

NETPROBE is intentionally non-destructive. It does not perform password attacks, exploit execution, malware deployment, persistence, data destruction, or unauthorized access. It is intended only for systems and websites that the operator owns or is explicitly authorized to assess.

---

# 2. Problem Statement

Organizations frequently expose network services and websites without having a centralized and repeatable understanding of their security weaknesses.

Manual assessment of the following activities is slow and inconsistent:

- Discovering reachable hosts
- Identifying open ports
- Detecting network services
- Collecting service banners
- Identifying software products and versions
- Checking HTTP and HTTPS configuration
- Validating TLS certificates
- Reviewing cookie security attributes
- Identifying exposed administrative or configuration paths
- Correlating detected versions with known vulnerabilities
- Documenting evidence and remediation guidance

A basic port scanner can report that TCP/80 or TCP/443 is open, but it does not necessarily explain the security meaning of that exposure. NETPROBE addresses this gap by converting raw network observations into structured security findings and actionable recommendations.

---

# 3. Project Aim

The aim of NETPROBE is to provide a compact, modular, explainable, and safe vulnerability assessment utility that helps authorized security administrators answer:

1. What assets and services are exposed?
2. What technologies and versions were detected?
3. Are insecure configurations present?
4. Does detected software potentially match known vulnerabilities?
5. What evidence supports the finding?
6. How confident is the detection?
7. What should be fixed first?
8. Did a remediation change the security state?

---

# 4. Project Objectives

The project objectives are:

- Provide TCP host and port discovery.
- Detect common services and protocols.
- Collect safe service banners.
- Fingerprint products and versions where evidence is available.
- Assess authorized websites using safe HTTP and HTTPS requests.
- Check security headers, cookies, redirects, TLS certificates, and exposed paths.
- Correlate detected products and versions with local vulnerability intelligence.
- Clearly label CVE matches as potential vulnerabilities rather than proof of exploitation.
- Calculate transparent risk levels with explanations.
- Save scan history in SQLite.
- Create baseline states and detect changes.
- Export results in TXT, JSON, CSV, and HTML formats.
- Provide a Linux installation path using an isolated Python virtual environment.
- Expose the application through a professional `netprobe` command.

# 9. Network Scanning Module

The network scanning module performs TCP connect scanning using configurable concurrency and timeouts.

## Features

- Single IPv4 targets
- Hostnames
- CIDR ranges
- Explicit IP ranges
- Comma-separated targets
- Individual ports
- Port ranges
- Common port groups such as `top20` and `top100`
- Open, closed, filtered, and error states
- Latency measurement
- Optional host discovery

## Example

```bash
python main.py network 192.168.1.10 --ports 22,80,443
```

or after Linux installation:

```bash
netprobe scan 192.168.1.10 --ports 22,80,443
```

## Output Information

For each target, NETPROBE can report:

- Target address
- Scan duration
- Number of scanned ports
- Number of open ports
- Number of closed ports
- Number of filtered ports
- Port number
- TCP state
- Detected service
- Connection latency

# 11. Product and Version Detection

NETPROBE analyzes service banners using known product patterns.

Examples of supported identification patterns include:

- OpenSSH
- Apache HTTP Server
- nginx
- MySQL
- MariaDB
- vsFTPd
- ProFTPD
- Postfix
- Exim
- lighttpd
- Microsoft IIS

The version detector returns:

```text
Product
Version
Confidence
Evidence
```

If the banner does not provide enough evidence, NETPROBE reports `Unknown` rather than inventing a version.

This reduces false vulnerability matches caused by unsupported or incomplete fingerprints.

# 12. Website Security Assessment

The website assessor performs safe, non-destructive checks against an explicitly supplied HTTP or HTTPS URL.

## HTTP Checks

- HTTP response status
- Redirect behavior
- Plaintext HTTP exposure
- Server header disclosure
- Directory listing indicators
- Forms posting to HTTP URLs

## Security Header Checks

- Strict-Transport-Security
- Content-Security-Policy
- X-Content-Type-Options
- X-Frame-Options
- Referrer-Policy

## Cookie Checks

- Secure attribute
- HttpOnly attribute
- SameSite attribute

## Exposed Path Checks

The assessor uses safe HEAD requests for high-signal paths such as:

```text
/.env
/.git/HEAD
/server-status
/phpinfo.php
/actuator/env
```

A path is reported only when it returns HTTP 200. The tool does not download sensitive files or attempt exploitation.

---

# 13. TLS Assessment

For HTTPS targets, NETPROBE uses certificate verification and TLS socket inspection.

The TLS assessor checks:

- Certificate trust validation
- Hostname validation
- Certificate expiry
- Certificates near expiry
- Negotiated TLS protocol
- Negotiated cipher
- TLS handshake failures

Possible TLS states include:

```text
Valid
Near Expiry
Expired
Validation Failed
Handshake Failed
Unknown
```

A failed certificate validation is reported as a security finding with evidence and remediation guidance.

# 14. Security Rule Engine

The security rule engine evaluates discovered services and configurations against defensive security rules.

Current rule categories include:

- Telnet exposure
- Plaintext FTP exposure
- Plaintext HTTP exposure
- Public database exposure
- RDP and VNC exposure
- SMB and NetBIOS exposure
- Website security header weaknesses
- Cookie security weaknesses
- TLS and certificate issues
- Information disclosure

Each rule finding contains:

```text

Target
Port
Service
Finding
State
Severity
Reason
Evidence
Confidence
Recommendation
```

The service matcher is protocol-aware. For example, `HTTPS` is not incorrectly treated as plaintext `HTTP`.

# 15. Vulnerability Correlation Engine

The vulnerability engine compares identified products and versions against local vulnerability intelligence in:

```text
data/vulnerabilities.json
```

The correlation flow is:

```text
Detected Product
       |
       v
Detected Version
       |
       v
Version Normalization
       |
       v
Affected-Version Comparison
       |
       v
Potential Vulnerability Match
```

Each matched vulnerability includes:

- NETPROBE finding ID
- CVE ID
- Product
- Vendor when available
- Detected version
- Affected versions
- Fixed versions when available
- Severity
- CVSS score
- CWE when available
- Confidence
- Status
- Impact
- Summary
- Remediation
- References

Example status:

```text
Potentially Affected
```

A version match is not described as proof that the target is exploitable.

# 17. Finding States

NETPROBE distinguishes observation from confirmation.

Current states include:

## Detected

A service or condition was observed.

## Verified Configuration Issue

A safe check directly demonstrated a configuration weakness, such as a missing header or insecure cookie attribute.

## Potentially Affected

A detected product and version matched a vulnerability intelligence record. This does not prove exploitability.

Future lifecycle states may include:

```text
Discovered
Potential
Validating
Confirmed
Needs Review
Reported
Remediation
Resolved
Reopened
```

# 18. Risk Analysis

NETPROBE calculates a transparent qualitative risk level using:

- Vulnerability severity
- CVSS score
- Security rule severity
- Service exposure
- Detection confidence
- High-risk service type
- Number and type of findings

Risk levels are:

```text
CRITICAL
HIGH
MEDIUM
LOW
INFO
```

Every risk result includes a rationale rather than an unexplained number.

Example:

```text
HIGH

Reasons:
- High-severity vulnerability match
- Exposed service detected
- Strong version evidence
- Remediation is available
```

# 23. Linux Packaging and Installation

The project has been prepared for Debian-family Linux systems.

Supported target environments:

- Debian
- Ubuntu
- Kali Linux
- Parrot OS

Installation process:

```bash
unzip NETPROBE.zip
cd NETPROBE
chmod +x install.sh
sudo ./install.sh
```

The installer:

1. Checks that the operating system is Linux.
2. Detects Python 3.
3. Creates an isolated environment under `/opt/netprobe`.
4. Copies the project source into `/opt/netprobe/source`.
5. Installs declared dependencies.
6. Creates `/usr/local/bin/netprobe`.
7. Runs version and doctor checks.
8. Prints usage instructions.

After installation:

```bash
netprobe --help
netprobe --version
netprobe doctor
```

The command works from any directory.

# 30. Limitations

NETPROBE is an assessment and correlation tool, not an exploitation framework.

Important limitations include:

- Version identification depends on available banner evidence.
- A potential CVE match does not prove exploitability.
- The local vulnerability database is limited to its stored records.
- Some services suppress banners or return generic responses.
- TLS checks depend on network reachability and certificate presentation.
- HTTP security checks observe the supplied URL and selected safe paths only.
- The current installation script must be executed on Linux for full validation.
- A Linux host must have Python 3 and virtual-environment support available.

These limitations are intentionally reflected through confidence and potential-status fields.
